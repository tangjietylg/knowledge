# LLM-Wiki

> **提出者：** Andrej Karpathy（OpenAI 联合创始人、前特斯拉 AI 总监），2026 年 4 月于 GitHub Gist 发布。
> 
> 相关阅读：[[rag-limitations|RAG 的局限]] — 理解为什么"现搜"不够

## 核心理念

> **让 LLM 成为"研究图书管理员"，主动维护一个持久的、结构化的 Markdown 知识库。**

核心思想是：**把"读"和"查"分离——离线完成理解与结构化，在线只做查询和推理。**

## 三层架构

| 层级 | 说明 | 特点 |
|:---|:---|:---|
| **Raw Sources**（原始资料） | 收集的论文、文章、图片等源文件 | 只读，不可变，作为真相来源 |
| **The Wiki**（维基本体） | LLM 生成的 Markdown 文件目录 | LLM 全权维护，人类只读 |
| **The Schema**（模式文档） | 如 `CLAUDE.md` 或 `AGENTS.md` | 配置 LLM 如何维护维基的规则 |

## 核心创新：编译 vs 检索

| | 传统 RAG | Karpathy 的 LLM Wiki |
|:---|:---|:---|
| **知识处理时机** | 查询时实时检索 | 摄入时一次性编译 |
| **知识持久性** | 无状态，每次从零开始 | 有状态，持续积累 |
| **跨文档关联** | 临时发现或遗漏 | 预构建并持续维护 |
| **矛盾检测** | 常被忽略 | 摄入时自动检测并标记 |
| **输出格式** | 临时聊天回复 | 持久的可编辑 Markdown 文件 |

## 工作流程

```
1. 数据摄入 → 将原始资料放入 raw/ 目录
2. 编译步骤 → LLM 读取源文件，生成结构化维基页面
              （摘要、概念页、实体页、双向链接）
3. 主动维护 → 定期"lint"检查：发现矛盾、缺失连接、过时内容
4. 查询使用 → 直接向 LLM 提问，基于已编译的维基回答
```

## 关键特征

- **[[Wiki-Links]]**：使用 Obsidian 风格的双向链接连接相关概念
- **Search Write-Back**：将搜索结果写回维基，形成知识复利循环
- **自愈合**：LLM 持续维护一致性，无需人工整理
- **数据主权**：纯 Markdown 文件，不锁定在任何平台

## 推荐工具栈

| 用途 | 工具 |
|:---|:---|
| 维基界面/编辑器 | **Obsidian**（本地优先，图谱视图） |
| AI 代理 | **Claude Code**（终端式，直接访问文件系统） |
| 网页剪藏 | Obsidian Web Clipper |
| 版本控制 | Git |

## 规模与性能

Karpathy 实测：约 **100 篇文章、40 万字** 的规模下，LLM 通过摘要和索引文件导航的效率仍优于传统 RAG 管道。

## 核心哲学

> *"Obsidian 是 IDE，LLM 是程序员，维基是代码库，你是架构师。"*

> *"你几乎从不手动编写或编辑维基；那是 LLM 的领域。"*

这是一种 **"文件优先于应用"（file-over-app）** 的理念——数据完全由用户拥有，AI 只是高度复杂的编辑代理。

## 与我们知识库的关系

我们的 `knowledge/` 目录本质上是 LLM-Wiki 的一个实例：
- `knowledge/` = The Wiki
- 各子目录的 README = Schema 定义
- Raw Sources 暂未建立（未来可补充）
