# AI-native 游戏生产：实践方法

## 核心原则

**先实体化，后应用。**

把"结构化"和"应用"分离——离线完成实体抽取和规格定义，在线只做 Pipeline 执行和 Skills 加工。

---

## 游戏生产路径：五步走

### 第一步：剧本实体化

从剧本中抽取核心实体，建立游戏世界的基础结构。

```
剧本原文
    ↓ LLM 辅助抽取 + 人工审核
角色 / 场景 / 道具 / NPC / 事件 / 规则 ...
```

每个实体必须包含：
- **基础元数据**：名称、类型、版本、状态
- **规格描述**：完整的上下文信息
- **关联关系**：与其他实体的连接
- **交付标准**：后续工种的产出规格

**这是最重要的步骤，Schema 设计决定整个生产系统的质量。**

### 第二步：实体 Schema 定义

为每类实体定义结构化 Schema。

游戏行业的核心实体 Schema：

| 实体类型 | 必须字段 | 可选字段 |
|:---|:---|:---|
| 角色 | 名称、性格、背景、关系 | 语音规格、美术风格、战斗属性 |
| 场景 | 名称、位置、氛围、触发事件 | NPC列表、可交互道具、规则 |
| 道具 | 名称、类型、效果、使用方式 | 美术规格、程序实现方式 |
| NPC | 名称、身份、行为模式、对话树 | AI行为规格、语音规格 |
| 事件 | 名称、触发条件、影响范围 | 后续剧情、奖励配置 |
| 规则 | 名称、逻辑描述、数值体系 | 测试用例、平衡性备注 |

**Schema 没有标准答案，只有游戏专家才能做这件事。**

### 第三步：Skills 开发

把每个工种的能力封装成 Skills。

游戏行业的 Skills：

| Skill | 输入 | 输出 | 适用场景 |
|:---|:---|:---|:---|
| 角色解析 Skill | 角色实体 | 性格分析、关系图谱、美术要点 | 角色设计前 |
| 场景解析 Skill | 场景实体 | 空间结构、氛围规格、美术要点 | 场景设计前 |
| 美术规格 Skill | 解析结果 | 美术需求文档、参考资料规格 | 美术制作前 |
| 程序接口 Skill | 美术规格 | 程序实现规格、AI行为规格 | 程序开发前 |
| 对话生成 Skill | NPC实体 | 对话树、语音规格 | NPC制作前 |
| 规则实现 Skill | 规则实体 | 程序逻辑、数值配置 | 规则开发前 |

**Skills 的设计原则见 `context-engineering/concepts/skill-design-principles.md`。**

### 第四步：Pipeline 编排

把多个 Skills 串成完整的生产 Pipeline。

```
剧本 → 实体抽取 Pipeline → 角色/场景/道具实体
                              ↓
                         美术加工 Pipeline → 美术资产
                              ↓
                         程序接入 Pipeline → 程序资产
                              ↓
                         游戏世界
```

Pipeline 需要定义：
- Skills 之间的时序和依赖
- 数据如何在 Skills 之间流转
- 异常处理和分支逻辑
- 人工审核节点

### 第五步：实体网络运营

实体不是一次性建完就结束的，需要持续运营：

| 工作 | 频率 | 负责方 |
|:---|:---|:---|
| 实体更新 | 按需 | LLM + 人审核 |
| Schema 迭代 | 定期 | 人（游戏专家） |
| 连接维护 | 定期 | 健康检查 |
| Pipeline 优化 | 按需 | 人 + LLM |

## 从剧本到游戏世界的完整流程

```
剧本（原始素材）
    ↓ 实体抽取
┌─────────────────────────────────┐
│  角色  场景  道具  NPC  事件  规则  │
│  （实体，带完整规格和元数据）      │
└─────────────────────────────────┘
    ↓ Skills 加工
角色 → 角色解析 → 美术规格 → 美术资产
场景 → 场景解析 → 关卡设计 → 关卡资产
道具 → 道具解析 → 程序规格 → 程序资产
    ↓ Pipeline 编排
┌─────────────────────────────────┐
│  多工种并行 → 产出汇聚 → 游戏世界  │
└─────────────────────────────────┘
```

## 工具链建议

| 环节 | 工具 | 说明 |
|:---|:---|:---|
| Schema 设计 | 手动设计 + 文档化 | 核心环节，工具辅助有限 |
| 实体抽取 | LLM API | Prompt 设计决定质量 |
| 图数据库 | Neo4j / TuGraph | 实体关系存储 |
| 向量检索 | Milvus / Pinecone | 语义召回 |
| Skills 管理 | OpenClaw Skills | 能力单元的封装 |
| Pipeline 编排 | OpenClaw Sessions | 流程的编排和执行 |
| 版本控制 | Git | 实体资产也需要版本管理 |

## 避坑指南

1. **不要跳过 Schema 定义**
   直接上 AI 抽取会产出一堆质量不可控的碎片，美术和程序无法直接使用。

2. **不要忽视人工审核**
   AI 抽取有幻觉，实体规格必须由游戏专家把关。

3. **不要追求一步到位**
   先从剧本的核心实体开始，逐步扩展到所有类型。

4. **不要脱离游戏设计**
   Schema 设计必须结合游戏设计逻辑，不是纯技术活。

5. **不要低估维护成本**
   实体网络需要持续运营，版本控制和一致性是关键。

## 与 Context Engineering 的关联

CE 框架是实体结构化的理论支撑：

| CE 概念 | 在游戏生产中的对应 |
|:---|:---|
| Input = Output | 实体规格 → 实体产出 |
| Schema 定义 | 实体 Schema（角色/场景/道具...） |
| 三方责任 | 工具供应商做 Skills，Schema 只有自己能做 |
| 健康检查 | 实体网络定期维护 |
| 连接设计 | 实体之间的关系（角色-场景、道具-NPC...）
