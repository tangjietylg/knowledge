# AI-native 组织转型：实践方法

## 核心原则

**先结构化，后应用。**

把"结构化"和"应用"分离——离线完成理解与结构化，在线只做查询和执行。

---

## 转型路径：五步走

### 第一步：Schema 定义

针对业务领域，人工设计实体类型和关系。

这一步是所有后续工作的根基：
- 定义知识节点有哪些字段
- 定义节点之间是什么关系
- 定义同义词归一化规则

**Schema 没有标准答案，只有业务专家才能做这件事。**

### 第二步：Structured Data 抽取

用 AI 辅助，把已有知识转成结构化格式。

```
原始内容（文档/SOP/经验）
    ↓ AI 辅助抽取
Structured Data（实体 + 关系 + 上下文）
```

关键要求：
- 输入格式标准化
- 输出格式标准化
- 人工审核确保质量

### 第三步：Skills 化

把能力封装成可复用的 Skills。

每个 Skill 需要定义：
- 输入格式（Structured Data）
- 输出格式（Structured Data）
- 适用场景
- 边界限制

**Skill 的设计原则见 `concepts/skill-design-principles.md`。**

### 第四步：Pipeline 编排

把多个 Skills 连成可执行的流程。

Pipeline 需要定义：
- Skills 之间的时序和依赖
- 数据如何在 Skills 之间流转
- 异常处理和分支逻辑

### 第五步：知识网络运营

知识库不是一次性建完就结束的，需要持续运营：

| 工作 | 频率 | 负责方 |
|:---|:---|:---|
| 节点更新 | 按需 | AI + 人审核 |
| 连接维护 | 定期 | 健康检查 |
| Schema 迭代 | 定期 | 人（业务专家） |
| Pipeline 优化 | 按需 | 人 + AI |

## SOP 升级路径

对于已有 SOP 的企业，升级路径如下：

```
现有 SOP（步骤 + 角色 + 工具 + 判断）
    ↓ 拆解
Structured Data（输入/输出/判断条件）
    ↓ 抽象
Skills（角色/工具 → 能力单元）
    ↓ 编排
Pipeline（步骤 → 时序关系）
    ↓ 验证
AI-native SOP
```

不需要从零开始，只需要用新的抽象重新表达已有的 SOP。

## 工具链建议

| 环节 | 工具 | 说明 |
|:---|:---|:---|
| Schema 设计 | 手动设计 + 文档化 | 核心环节，工具辅助有限 |
| 数据抽取 | LLM API | Prompt 设计决定质量 |
| 图数据库 | Neo4j / TuGraph | 关系存储 |
| 向量检索 | Milvus / Pinecone | 语义召回 |
| Skills 管理 | OpenClaw Skills | 能力单元的封装 |
| Pipeline 编排 | OpenClaw Sessions | 流程的编排和执行 |
| 知识管理 | Obsidian / Logseq | 个人/小团队知识库 |
| 版本控制 | Git | 知识库也需要版本管理 |

---

## 避坑指南

1. **不要跳过 Schema 定义**
   直接上 AI 抽取会产出一堆质量不可控的碎片。

2. **不要忽视人工审核**
   AI 抽取有幻觉，必须有人工把控质量。

3. **不要追求一步到位**
   先做核心实体和核心流程，逐步扩展。

4. **不要脱离业务**
   Schema 设计必须结合业务需求，不是纯技术活。

5. **不要低估维护成本**
   知识网络需要持续运营，不能建完就撒手。
