# 02 核心概念澄清

## Context Engineering 是什么

**Context Engineering 是解决"AI 输入质量"问题的实践体系。**

它不关注 Agent 的架构设计，不关注模型本身的能力边界，而是专注于：**如何组织输入给 LLM 的内容，让输出质量更高。**

## LLM 输入的复合结构

LLM 的输入不是单一的"问题"，而是多层次的复合结构：

| 组成部分 | 来源 | 说明 |
|---------|------|------|
| System Prompt | Agent 模块 | 角色定义、能力边界、行为约束 |
| User Query | 用户 | 即时请求，通常很短 |
| Conversation History | Agent 模块 | 多轮对话上下文 |
| Retrieved Context | 知识库 | 从外部知识库召回的内容 |
| Tool Outputs | Agent 模块 | 搜索、代码执行等工具结果 |
| User-provided Artifacts | 用户 | 上传的文件、表格、结构化数据 |

## 关键洞察：三方责任框架

把输入拆开看之后，会发现一个极其重要的真相——**Context Engineering 的各部分，由不同的责任方承担**：

| 输入组成部分 | 责任方 | 谁能做 |
|-------------|--------|--------|
| System Prompt | Agent 模块 | 开源社区 / 技术供应商 ✓ |
| Chat History | Agent 模块 | 开源社区 / 技术供应商 ✓ |
| Tool Outputs | Agent 模块 | 开源社区 / 技术供应商 ✓ |
| User Query | 用户 | 用户自己 ✓ |
| Retrieved Context | **知识库** | **企业/个人自己** ← 无法外包 |

**开源社区能帮你搭 Agent 框架，大厂能帮你提升模型能力，但 Retrieved Context 的质量——也就是知识库——没有任何人能替你做。**

这不是因为技术不够，而是因为这个问题本质上是**归属问题**：企业剧本里的知识结构只有企业自己能定义，个人知识库里的卡片只有个人自己能整理。

> **这也意味着：把精力放在模型选型和 Agent 架构上，最终是可以抄作业的。但数据治理这件事，没有标准答案，只能自己动手。**

好消息是，一旦把这件事做好了，模型和工具的每一次进步，都只是在给你的数据基础设施加马力——你不是在被替代，而是在被放大。

## 核心推论

> **大模型和 Agent 再怎么进步，有一部分是他们永远做不了的。**

技术会标准化，但数据不会标准化。

## Context Engineering ≠ Harness/Agents

| | Harness/Agents | Context Engineering |
|---|---|---|
| 解决的问题 | WHAT | HOW |
| 核心关注 | 定义边界、流程、工具 | 怎么组织输入、怎么治理数据 |
| 层次 | 架构层 | 实践层 |
| 责任方 | 技术供应商 | 企业/个人 |

**Harness** 定义的是"AI 能做什么"——用哪些工具、遵循什么流程、行为边界是什么。

**Context Engineering** 定义的是"如何让 AI 做好"——输入的内容结构好不好、数据质量行不行、上下文在正确时间出现正确内容没有。

这不是上下级关系，而是两条并行的线。

## Agent 侧的子模块

从输入组装的视角，Agent 侧包含多个子模块，每个都影响最终给 LLM 的内容：

| 子模块 | 职责 | 说明 |
|--------|------|------|
| Prompt Builder | 格式化用户 query，组装结构化 prompt | 把自然语言转成模型友好的格式 |
| Context Engine | 管理上下文窗口，决定截断和保留策略 | 解决上下文长度限制 |
| Memory Manager | 维护短期记忆和长期记忆的分层 | 历史信息怎么管理 |
| Retriever | 从知识库召回相关内容 | 召回策略决定上下文质量 |
| Tool Integrator | 把工具执行结果拼进上下文 | 扩展 LLM 的能力边界 |

这些子模块的技术会由开源社区持续迭代，但它们解决的仍然是**"怎么组织输入"**的问题，输入原材料本身的质量——Retrieved Context——仍然是知识库侧的责任。

## 为什么 Context Engineering 被忽视

1. **看不见**：Agent 有炫酷的架构，Context Engineering 只有枯燥的数据治理
2. **难标准化**：每个公司的剧本结构不一样，无法用通用方案解决
3. **短期看不到效果**：数据治理的收益是长期的，但成本是即时的
4. **论证链条没有显性化**：很多人隐约感觉到问题，但没有从输入结构出发把"谁的职责"讲清楚

## 核心公式

```
输出质量 ≈ f(模型能力, 输入质量)

模型能力      → 随技术进步不断提升（供应商负责）
输入质量      → 需要自己做（企业和个人负责）
  ├── Agent 侧模块 → 技术供应商负责
  └── Retrieved Context → 企业/个人自己负责 ← 唯一瓶颈
```

**一旦 Retrieved Context 的质量上去了，模型能力和 Agent 技术的提升全是红利——而不是相反。**
