# 03 实践方法

## 核心原则：先结构化，后应用

Context Engineering 的实践分为两个阶段：

1. **离线阶段**（一次性投入，持续维护）
2. **在线阶段**（每次查询）

把"读"和"查"分离——离线完成理解与结构化，在线只做查询和推理。

## 离线阶段：知识结构化

### Step 1：定义 Schema

针对垂直领域，人工设计实体类型和关系。

以游戏剧本为例：

| 实体类型 | 示例 | 关键属性 |
|---------|------|---------|
| 人物 | 李逍遥、赵灵儿 | 身份、性格、背景、人物关系 |
| 地点 | 苏州、仙灵岛 | 地理位置、势力归属、描述 |
| 技能 | 御剑术、酒神咒 | 类型、效果、使用条件 |
| 物品 |  sword、灵蛊 | 归属、效果、获取方式 |
| 组织 | 蜀山派、拜月教 | 势力范围、成员、目标 |
| 势力 | 正道、魔道 | 立场、关系、动态 |

Schema 设计决定后续所有工作的质量，需要结合业务深度打磨。

### Step 2：LLM 辅助抽取

用大模型按 Schema 抽取实体实例。

```
输入：剧本原文
输出：按 Schema 结构化的实体列表

示例：
{
  "type": "人物",
  "name": "李逍遥",
  "attributes": {
    "身份": "蜀山派弟子",
    "性格": "侠义心肠",
    "背景": "..."
  },
  "relations": [
    {"type": "师徒", "target": "剑圣", "context": "..."},
    {"type": "恋人", "target": "赵灵儿", "context": "..."}
  ]
}
```

### Step 3：人工审核和质量把控

LLM 抽取的结果需要人工审核，确保：
- 实体分类正确
- 属性填充完整
- 关系描述准确
- 无矛盾和遗漏

### Step 4：存入结构化知识库

根据场景选择合适的存储：
- **图数据库**：适合实体关系复杂的场景（Neo4j）
- **向量数据库**：适合语义检索场景（Pinecone、Milvus）
- **混合存储**：结构化数据存图数据库，向量索引存向量数据库

## 在线阶段：查询与推理

### 查询策略

1. **精确查询**：根据实体 ID 或属性精确查找
2. **语义查询**：根据描述语义召回相似实体
3. **关系查询**：查询实体间的关联路径
4. **组合查询**：结合多种条件过滤

### 上下文组装

根据任务需求，从知识库组装上下文：

```
用户任务：续写李逍遥在蜀山派的故事

组装上下文：
1. 李逍遥的完整人物档案（属性、关系）
2. 蜀山派的基本信息（地点、势力、成员）
3. 近期剧情事件（维持连贯性）
4. 相关人物档案（剑圣、酒剑仙等）
```

### 与 LLM 交互

把组装好的上下文作为 Retrieved Context 的一部分输入 LLM，结合 System Prompt 定义角色和行为约束。

## 持续维护

知识库不是一次性建完就结束的，需要：

1. **增量更新**：剧本更新时，同步更新知识库
2. **质量监控**：定期检查实体完整性和一致性
3. **Schema 迭代**：随着对业务理解加深，持续优化 Schema

## 工具链建议

| 环节 | 工具 | 说明 |
|------|------|------|
| Schema 设计 | 手动设计 + 文档化 | 核心环节，工具辅助有限 |
| 实体抽取 | LLM API (Claude/GPT) | Prompt 设计很重要 |
| 图数据库 | Neo4j / TuGraph | 关系存储首选 |
| 向量检索 | Milvus / Pinecone | 语义召回 |
| 知识管理 | Obsidian / Logseq | 个人知识库可参考 |
| 版本控制 | Git | 知识库也需要版本管理 |

## 避坑指南

1. **不要跳过 Schema 设计**：直接上 LLM 抽取会产出一堆质量不可控的碎片
2. **不要忽视人工审核**：LLM 抽取有幻觉，必须有人工把控
3. **不要追求一步到位**：先做核心实体，逐步扩展
4. **不要脱离业务**：Schema 设计必须结合业务需求，不是纯技术活
