# RAG 的局限

## 核心问题：检索 ≠ 理解

RAG（Retrieval-Augmented Generation）解决的是"用时现搜"的问题——当用户提出问题时，从大量文档中召回相关片段，拼进上下文。

但这有两个根本性局限：

### 1. 召回的是"相关片段"，不是"完整认知"

例子：要了解某个游戏人物的一生，RAG 只能返回"提到了这个人物的几个段落"。但这些段落可能：
- 散落在剧本各处，召回时只返回片段
- 不包含人物的成长轨迹和性格转变
- 不包含人物与其他实体的隐含关系

**真正的理解需要通读全貌，而不是关键词匹配。**

### 2. 每次都是独立召回，无法保证一致性

RAG 对话式调用中，前后多次召回的内容可能存在矛盾，或者遗漏之前已经提过的关键信息。

对于长剧本创作，这会导致：
- 前后矛盾（人物关系、势力范围等）
- 信息丢失（第二章提到的细节，第五章调用时忘了）
- 碎片化（召回的内容像拼凑的积木，而不是完整的知识体系）

## RAG 适合的场景

- 简单的事实查询（「某个 API 怎么用」）
- 文档摘要（「这篇文章讲了什么」）
- 开放域问答

## RAG 不适合的场景

- 需要完整理解（「这个人物的生平、性格、成长轨迹」）
- 需要一致性和完整性（「写第三章时调用所有相关信息，不能遗漏」）
- 垂直领域深度知识（「游戏剧本中的势力关系、技能体系、物品设定」）

## 根本矛盾

RAG 的本质是"检索"，但知识的核心是"关联"和"完整性"。

要解决这个矛盾，必须把「读」和「查」分离：
- **离线阶段**：通读、理解、结构化 → 输出到知识库
- **在线阶段**：只管查询，不用重复读原始材料

这就是 LLM-Wiki 的核心思想。
